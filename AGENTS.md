# SICOSIG

LangGraph proof-of-concept agent: brief A→B directions for Madrid public
transport. OpenAI-compatible chat model (DeepInfra by default, ollama/llama.cpp
for local serving) + Madrid Transport MCP server (stdio) + local GTFS route
planner.

## Structure

- `sicosig.py` — CLI entry point (one-shot query via argv or interactive
  REPL); stage feedback goes to stderr via the agent's `status` callback
- `agent/__init__.py` — model, MCP client, langgraph agent (`SicosigAgent`)
  and the `plan_route` tool (langchain `@tool` wrapping the router, with an
  `avoid` param for line names). `ask()` wraps the agent loop: run the loop
  (streamed, emits tool-call stages) and ONLY once an itinerary has been
  proposed fetch alerts + verify with verify.py (no itinerary → no
  verification, no data fetch); a compromised verdict is reported back to
  the agent (`[VERIFICACION]` user message) up to
  `MAX_VERIFICATION_ROUNDS` replans; the final pass is not re-verified so
  the agent always answers (informed by previous reports)
- `agent/router.py` — CSA route planner over `agent/data/network.db`
  (metro frequency-expanded + cercanías/interurbano stop_times,
  walk transfers); `plan_avoiding` resolves line names to route_ids and
  excludes them; every leg carries its `route_id`
- `agent/models/` — pydantic contracts shared between the tool loop and
  the verification loop: `Leg`, `Itinerary`, `PlanError` (union
  `PlanResult`, discriminated by `kind`), `Alert`, `Verdict`. The router
  stays dict-based; the pydantic boundary is `plan_route` itself
  (`itinerary`/`error`/`dump` helpers) and `itinerary_of` re-validates
  the tool message with `Itinerary.model_validate_json`
- `agent/verify.py` — itinerary verification prompt (`VERIFY_PROMPT`), a
  separate stage above the agent loop: `check_itinerary` crosses leg
  route_ids against active alerts (no id match → no LLM call) and the
  judge prompt decides whether the alert text truly compromises the trip
  (suspension/cut vs mere delays); unparseable verdicts fall back to
  conservative id matching. `report_message` formats the agent report
- `agent/alerts.py` — active service alerts (Renfe GTFS-RT ServiceAlerts,
  no auth: gtfsrt.renfe.com/alerts.json, selectors routeId/stopId match
  network.db ids; only Madrid `10T*` selectors are kept), crossing them
  with proposed itineraries (`compromised_legs`). Metro/CRTM/EMT expose no
  public alerts API today (EMT requires credentials; ayuntamiento only
  publishes road-traffic XML) — add new sources as extra fetchers in
  alerts.py
- `agent/data/network.db` — generated by the update script, gitignored
- `scripts/update_gtfs.py` — downloads CRTM GTFS feeds and integrates them
- `tests/test_agent.py` — config/unindent tests, no API key needed
- `tests/test_alerts.py` — Renfe feed parsing and leg/alert crossing
- `tests/test_models.py` — pydantic contract round-trips, no API key
- `tests/test_router.py` — router tests over a synthetic GTFS feed
- `tests/test_verify.py` — judge verdict parsing, fallback and report
- `mcp-madrid-public-transport/` — third-party MCP server (TS, node, stdio)

## Conventions

Plain python, single quotes, two blank lines between top-level defs, no type
hints (pydantic model fields are the one exception: they are the library's
API), unittest for tests. Functions as short as possible: one job each,
early guards, compose small helpers (see blockpy's majority →
choose_majority → accumulate_members). Config through `.env` (see
`.env.example`).
The update script is stdlib-only (urllib/zipfile/sqlite3), idempotent,
safe to re-run.

## Commands

- install: `pip install -r requirements.txt` (venv), MCP: `npm install && npm run build` inside `mcp-madrid-public-transport/`
- data: `python scripts/update_gtfs.py` (re-run weekly-ish to refresh feeds)
- tests: `python -m unittest discover tests`
- run: `python sicosig.py <pregunta>`

## Notes

The MCP server exposes real-time arrivals (metro, cercanías, bus EMT);
A→B routing (metro, cercanías and interurban buses) is done by
`plan_route` from CRTM GTFS schedules, never from the model's memory.
Alert checking is NOT inside the tool and stays lazy: alerts are fetched
and `verify.py` checks the proposed itinerary only after the agent loop
has proposed one (no itinerary → no verification, no fetch). A
compromised verdict is reported back so the agent replans with
`plan_route(avoid=[...])` or informs the user.
Real-time data source state: metro works live; cercanías station search
is fixed by the update script but expected arrivals can still be empty
(Renfe GTFS-RT only publishes vehicle positions, no trip updates); the
EMT/CRTM bus tools need credentials, but interurban routes already plan
from schedules.

GTFS integration (`scripts/update_gtfs.py`):

- Feeds from the CRTM ArcGIS hub (datos.crtm.es), download = ArcGIS item
  `/data` endpoint, no auth: metro `google_transit_M4.zip`, cercanías
  `google_transit_M5.zip`, interurbanos `885399f83408473c8d815e40c5e702b7`
  (also downloadable: EMT M6, urbanos, metro ligero). Interurbano goes into
  `transport-data/bus/interurban/` and its stops are `par_8_*`.
- The M5 feed unzips as-is into `transport-data/train/gtfs-static/` and
  `transport-data/metro/` is refreshed with M4; stale `*.txt.zip` sidecars
  are removed. `transport-data/train/stops.txt` is generated with
  `par_5_`-prefixed stop ids (the MCP in-memory store detects mode by
  prefix; numeric suffix = `CODIGOEMPRESA` used by the RT adapter).
- `gtfs-static.db` (+`.zip`) is rebuilt from M5 with the same schema as
  `SqliteGtfsStaticRepository.ts`; trip ids match the Renfe GTFS-RT feed
  1:1 (verified). The server must run with `cwd` = its own dir (relative
  `GTFS_DATA_PATH`); `better-sqlite3` was bumped to `^13.0.3` in its
  `package.json` because `12.4.1` doesn't compile on node 26.
- Router specifics: metro runs on frequencies (templates in `trips` with
  `freq=1` + `frequencies.txt`, expanded at query time); cercanías uses
  exact stop_times. Walk transfers: same `parent_station` 150s, any stops
  ≤250m 300s. The M4 metro feed is published late (valid through
  2026-05): when a feed has no calendar match for today the planner
  reuses the weekday pattern and sets `warning` in the result. That feed
  also lacks line 3 (closed in its snapshot): stations like Lavapiés are
  unreachable by metro there.

Model note: the agent requires tool calling. For fully local serving use a
tool-capable model via `SICOSIG_BASE_URL`/`SICOSIG_MODEL`, never gemma3
(it can't call tools: empty tool args on DeepInfra, "does not support
tools" on ollama). `qwen3.5:4b` (ollama) and Qwen3-4B on llama.cpp are
verified working through the OpenAI-compatible endpoint.
